# Management core — Group 4A approved design and implementation

**Status:** The target below was approved for Group 4A Build. Distinguish this design basis from behavior that is implemented and browser-reviewed; update the implementation/verification notes only after observing the rendered result. This override inherits the shared LumiPark tokens, Be Vietnam Pro, Light Glassmorphism 2.0, Tailwind v4, Lucide, and shared shell from [MASTER](../MASTER.md). It does not define new business, RBAC, authentication, or data-retention policy.

## Information architecture

### `/households`

- The entry view offers one search context at a time: **Hộ gia đình** or **Cư dân**, with URL-backed search and server pagination.
- Selecting a household opens an in-main household workspace: identity/contact, effective two-wheel/car quota with default-vs-explicit source, active vehicle usage where the caller is authorized to receive it, and a list of residents belonging to that household.
- Selecting a resident opens a read-only profile; Edit switches the main content to one sectioned editor. Add resident from a household presets that household. Do not append the long form after multiple global tables or show a redundant record-picker inside the editor.
- Household code is the current lookup/upsert key, not a proven renameable ID. During edit keep the identity stable; create/update wording must follow the server-confirmed result.
- A move to another household explains that owned vehicles may transfer, incompatible authorizations may be removed, and destination quota can reject the save. A summary is advisory; the server remains authoritative.

### `/vehicles`

- A server-searchable/paginated result table opens a read-only vehicle profile, then a focused in-main create/edit form. Do not keep the full form below the table or require a second record Select after a row has been chosen.
- In the editor distinguish household, registered owner, and per-vehicle authorized people. The owner is always included; other people are selected only from the chosen household.
- **Vehicle select overflow correction (2026-11-02, before implementation):** `#vehicleHousehold` and `#vehicleOwner` remain native selects with their existing full option labels/values and form names. Constrain the actual select controls (and their grid items) at all viewport sizes, not `.select-entity`/`selectedcontent` markup that these controls do not have. Keep the full native picker options and the existing household/owner/member filtering; selected display text may clip/ellipsize within the field, with the native option remaining available when reopened. Do not mask document overflow.
- Show the applicable car/two-wheel quota and whether it is default or household-specific. Usage counts active registered vehicles and exclude the vehicle being edited. The display is advisory; save validation is authoritative. Fuel type does not imply charging rights.
- Show whether a stored registration image exists and preview only a selected replacement. Do not turn a storage path into a public URL or fetch the old private image without an approved read permission/route.

### `/security-audit`

- Keep the server-filtered event table as the primary content. Compact date/outcome filters remain visible; less frequent actor/action search may be disclosure content on narrow screens.
- Preserve URL state, inclusive `Asia/Ho_Chi_Minh` date semantics, literal case-insensitive actor/action substring semantics, exact case-insensitive outcome matching, and 25 events per page.
- Display a human-readable known-action label with its unchanged technical code; unknown events retain the raw code. Explain that “người thực hiện” is the event actor; attempted login usernames can instead be targets.
- Distinguish no events, no filter matches, invalid filters, unavailable query and out-of-range page. Long references/reasons wrap or expand through keyboard-operable controls.
- Do not invent KPIs, event sources, sort, export, deletion, or evidence links.

### `/settings`

- Keep one narrow two-field form. Show saved vs changed values, a local revert-to-loaded-values action, submit feedback and a draft-leave warning.
- Explain that blank household overrides inherit, `0` is an explicit zero cap, and lowering a default does not delete/deactivate existing vehicles.
- Preserve permission-gated household link, existing POST/CSRF and unknown-write outcome messaging.
- **Pending-submit recovery decision (2026-11-02, before implementation):** after a valid changed native submit, synchronously mark the form `aria-busy="true"`, expose “Đang lưu hạn mức…” feedback, and block repeat submit/reset/edit while the response is pending. Keep successful controls enabled/serializable (use readonly for the numeric fields, not disabled), so the existing POST still carries both limits and CSRF. A no-op remains blocked as before; native required/min/integer validation is unchanged. If the document returns from the back-forward cache, clear only the transient pending lock and recompute the existing draft/reset state from retained values; never retry the POST or claim success client-side. This is a local settings-form interaction, not an idempotency or payment-policy change.
- **History-restored draft clarification (2026-11-02, post-implementation, prompted by native history evidence; not part of the initial design basis):** compare the live numeric input values with each control’s server-rendered `defaultValue`, not its potentially browser-restored `.value` at script initialization. Recompute draft state on every `pageshow`, including non-persisted history returns, while clearing a pending lock only on a persisted return. A retained value that differs from the rendered default must remain an actionable draft (save enabled/reset enabled), with no POST replay or success claim; exact BFCache use remains a separate observation.

### `/account/password`

- Keep the password page standalone so forced-change principals do not receive management navigation. Show different explanatory copy for forced and voluntary changes, and provide a CSRF logout action for the forced route.
- Use current/new/confirmation fields with password-manager autocomplete and paste, independent show/hide controls, linked errors and the existing login-again recovery after a successful/uncertain result.
- Preserve exactly the source policy: minimum 12 Java UTF-16 code units and maximum 72 UTF-8 bytes. Do not add composition rules, trimming, password-history checks or change session revocation.

## Shared interaction rules

- One active draft at a time. Selection, mode changes, Back, cancel and leave all preserve context or ask before discarding.
- Use native form/navigation semantics and progressive enhancement. The current POST endpoints remain available without JavaScript. A client-side request may keep a loaded form/file input in place for known server errors; it cannot promise draft persistence after reload, session expiry or document destruction.
- Identify loading, validation, success, conflict, permission/session failure and unknown write outcome separately. Use field-linked errors and a focusable summary after a failed multi-error submission. Never automatically replay an unknown POST.
- QR is autofill assistance, not proof or verification: preview returned values and explicitly apply them; do not overwrite non-empty differing user values silently. Late responses from a previous selected person are ignored.
- Resident face media remains permission-gated. No PII, raw QR, image or password in URL, browser storage, telemetry or screenshots.
- Use opaque data surfaces, existing semantic colors and visible focus. Table layouts may have a labeled horizontal scroll region only when necessary; essential actions/identity must not be hidden by responsive truncation.

## Pattern choice and rationale

- **Household/resident:** contextual record workspace rather than two global lists plus appended forms. The household–resident relationship and quota become the organizing context; detail stays read-first and editing remains on the same route family.
- **Vehicle:** table → profile → focused editor. Relationships and quota are ordered before technical/document fields so a save decision starts with the household/owner context.
- **Audit:** dense semantic table, not dashboard or timeline, because operators compare event time/actor/action/outcome and need stable server pagination.
- **Settings/password:** retain short native forms; add only feedback/recovery that addresses observed gaps.
- The UI UX Pro Max generator output was evaluated but not adopted: its property query recommended a marketing hero, teal/luxury typography and virtual-tour content. Focused UX/HTML-tailwind findings inform error recovery, focus visibility, password managers, reflow and responsive behavior; they do not supersede this approved system.
